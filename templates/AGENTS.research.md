## 每轮开始必须做

1. 读 `.auto/goal.md` —— 方法、目标、看哪些指标、大致方向、我的临时建议（**每次都要重读，我可能刚改过**）
2. 读 `.auto/notes.md` —— 当前状态、已验证有效、死胡同
3. 看 `.auto/runs.txt` —— 有哪些实验在跑

## 每一轮怎么工作

这是一个**不停的迭代循环**——没有"做完"这回事，除非我叫停（Esc）。

你的目标不是"把实验跑完"，而是**让方法和代码持续变好**。实验只是验证手段，
它存在的意义是告诉你这次改得对不对。

一轮的节奏：

1. **看上一轮的结果**（`DONE` / 日志），判断这次改动值不值
2. **想清楚下一步改什么** ← 这一步最重要，别急着动手
   - 结果变差了？先搞清楚为什么：是方向不对，还是实现有 bug、超参没调好、评测口径变了？
   - 没想明白就先**调研**：读论文、查有没有现成的模块/手法、看同类问题别人怎么解的
   - **调研充分再动手**——跑错方向比多花时间查资料贵得多
3. **改方法 / 改代码**
4. **起实验验证**（记得写 `DONE` + 调 `track_run` 登记）
5. **更新 `.auto/notes.md`**，然后结束这一轮

几个提醒：

- **别原地打转**：同一个想法试 2~3 次没效果就换方向，并把「试过、没用」写进死胡同
- **调研是工作的一部分**，不是拖延
- **死胡同比成功经验值钱**：跑几十轮以后，「什么不该再试」最能救命
- **不要只被动响应实验**：实验告诉你结果，但下一步往哪走得你自己想

## 服务器与实验（最关键，一步步照做）

**怎么起实验你决定**——`nohup`、`sbatch`、`docker run`、`conda run` 都行，扩展不干涉。
但下面 4 步必须全做：

**1. 起实验，并拿到进程号**

```bash
ssh <别名> "cd /项目 && nohup python train.py > /输出目录/log.txt 2>&1 & echo \$!"
```

最后那个数字就是进程号。

**2. 保证实验结束时会写 `DONE`**

- 最好**改训练代码**，让它跑完把指标写进 `<输出目录>/DONE`
- 或者命令末尾追加：`... ; touch <输出目录>/DONE`
- `DONE` 里放你的实验结果（指标、关键数字）——这是唯一的自动信号

**3. 立刻调 `track_run` 登记**

```
track_run(path="<输出目录的服务器绝对路径>", pid="<第 1 步的进程号>")
```

- pid **可选但强烈建议填**：填了崩了**立刻**通知，不填只能等 72 小时超时
- Slurm / Docker 拿不到 pid 就留空

**4. 之后不用管，扩展每 60 秒盯它**

> ⚠️ **漏掉第 2 步或第 3 步 → 这个实验永远不会有人等它，也不会有任何报错。**

## 收到通知后（完成 / 崩溃 / 超时）

1. 读那个路径下的 `DONE`（崩溃的话读它的日志定位原因）
2. **把那一行从 `.auto/runs.txt` 删掉**（不删会一直被查）
3. 按 `.auto/goal.md` 判断值不值，决定保留还是回滚
4. 更新 `.auto/notes.md`
5. 起下一个实验（回到上面 4 步）

## 每轮结束必须做

**重写** `.auto/notes.md`（不是追加，保持精简），含：

- 当前状态：正在验证什么、最近结果、下一步
- 已验证有效
- **死胡同**：明确不要再试的，及原因 ← 最重要
- 环境坑

## 其他约定

- 起实验前先调 `gpu_status` 查实时空闲卡
- **并发上限见 `.auto/goal.md`**（多人共用的服务器务必设上限，不要占满）
- 不动别人的进程、文件、环境
- 登记超过 72 小时还没有 `DONE`，扩展会提醒——通常意味着崩了或忘了写 DONE

### SSH 使用纪律（排查问题必读）

- 排查服务器问题**可以自由使用 ssh**（看日志、查进程、kill、nvidia-smi……），但**必须走正门**：
  `ssh <别名> '<任意命令>'`（原生 ssh + `~/.ssh/config` 里配好的别名，即配置里的 `sshHost`）
- **禁止 `wsl ssh`**（Windows 的 WSL 是另一套没配置的环境：独立的钥匙和指纹记录，会卡在指纹确认/缺钥匙）
- **禁止 `ssh 用户@裸IP`**（绕过别名配置，同样会卡交互确认）
- 不确定别名时看 `.pi/research-loop.json` 里的 `sshHost` 字段

## 代码管理

- 不强制 commit，但要保证改动可追溯（你可以在起实验时顺手记一下当前的 `git rev-parse HEAD`）
- 决定回滚时自己 `git checkout`，并说明原因
- 不要在一个失败上无限重试；试 2~3 次还不行就换方向，把原因写进死胡同

## 调研

- 优先读本地 `refs/`（论文、repo 笔记）
- 需要查新东西时用联网搜索工具
- 外部模块/包在写进方案前先确认它真的存在

## 结果判读

- 多指标往往有权衡（例如主指标涨但副作用指标也涨），**由你判断值不值**，不要只看单一数字
- 具体看哪些指标、怎么算"变好"，按 `.auto/goal.md` 里我写的口径
