## 每轮开始必须做

1. 读 `.auto/goal.md` —— 方法、目标、看哪些指标、大致方向、我的临时建议（**每次都要重读，我可能刚改过**）
2. 读 `.auto/notes.md` —— 当前在哪、最近结果、已知死胡同
3. 看 `.auto/runs.csv` —— 有哪些实验在跑
4. **需要回头看之前试过什么、或想回溯到某个节点时**，才读 `.auto/tree.md`
   （它记录了每一次尝试和对应的 commit，会一直变长，**不要每轮读**）

## 每一轮怎么工作

这是一个**不停的迭代循环**——没有"做完"这回事，除非我叫停（Esc）。

你的目标不是"把实验跑完"，而是**让方法和代码持续变好**。实验只是验证手段，
它存在的意义是告诉你这次改得对不对。

一轮的节奏：

1. **看上一轮的结果**（`DONE` / 日志），判断这次改动值不值
2. **想清楚下一步改什么** ← 这一步最重要，别急着动手
   - 结果变差了？先搞清楚为什么：是方向不对，还是实现有 bug、超参没调好、评测口径变了？
   - 没想明白就先**调研**：读论文、查有没有现成的模块/手法、看同类问题别人怎么解的
   - **调研充分再动手**——跑错方向比多花时间查资料贵得多
3. **改方法 / 改代码**
4. **起实验验证**（先查空闲卡 → 保证会写 `DONE` → 调 `track_run` 登记）
5. **更新 `.auto/notes.md`**，然后结束这一轮

几个提醒：

- **别原地打转**：同一个想法试 2~3 次没效果就换方向，并把「试过、没用」写进死胡同
- **调研是工作的一部分**，不是拖延
- **死胡同比成功经验值钱**：跑几十轮以后，「什么不该再试」最能救命
- **不要只被动响应实验**：实验告诉你结果，但下一步往哪走得你自己想

## 服务器与实验（最关键，一步步照做）

**怎么起实验你决定**——扩展不干涉、也不需要知道。下面 4 步必须全做：

> **为什么下面强调「服务器上的绝对路径」**：扩展每 60 秒 ssh 上去执行一句
> `test -f <路径>/DONE`，**它只认这一个信号**。相对路径、本地路径它都看不到。

**0. 摸清这台服务器的环境**

不同机器差别很大（裸机 / Slurm / Docker / 云 GPU 平台），起实验前探一下：

```bash
ssh {{SSH_ALIAS}} "which sbatch; which docker; which conda; nvidia-smi -L"
```

按探到的结果自己决定怎么起（需要 conda 就写在命令里：`conda run -n <环境名> python ...`）。
拿不到进程号就让它空着（Slurm 作业号、`docker` 都不算 pid），靠 `DONE` 也一样能等到。

> **判断错了不会报错，只会让实验永远没人等**——所以这步别省。

**1. 起实验，并尽量拿到进程号**

```bash
ssh {{SSH_ALIAS}} "cd /项目 && nohup python train.py > /输出目录/log.txt 2>&1 & echo \$!"
```

最后那个数字就是进程号（裸机才有；Slurm / Docker 见上表，留空）。

**2. 保证实验结束时会写 `DONE`**

- 最好**改训练代码**，让它跑完把指标写进 `<输出目录>/DONE`
- 或者命令末尾追加：`... ; touch <输出目录>/DONE`
- `DONE` 里放你的实验结果（指标、关键数字）——这是唯一的自动信号

**3. 立刻调 `track_run` 登记**

```
track_run(path="<输出目录的服务器绝对路径>", pid="<第 1 步的进程号>")
```

- pid **可选但强烈建议填**：填了崩了**立刻**通知，不填只能等 72 小时超时
- Slurm / Docker 拿不到 pid 就留空

**4. 之后不用管，扩展每 60 秒盯它**

> ⚠️ **漏掉第 2 步或第 3 步 → 这个实验永远不会有人等它，也不会有任何报错。**

## 收到通知后（完成 / 崩溃 / 超时）

1. 读那个路径下的 `DONE`（崩溃的话读它的日志定位原因）
2. **把那一行从 `.auto/runs.csv` 删掉**（不删会一直被查）
3. 按 `.auto/goal.md` 判断值不值，决定保留还是回滚
4. 更新 `.auto/notes.md`
5. 起下一个实验（回到上面 4 步）

## 每轮结束必须做

**1. 重写 `.auto/notes.md`**（不是追加，保持精简——它每轮都会被读）：

- 当前节点、正在验证什么、最近结果、下一步打算
- **死胡同**：明确不要再试的，及原因 ← 最重要
- 环境坑

**2. 更新 `.auto/tree.md`**（累积记录，按需才读，所以可以详细）：

每试一个新方向就追加一个节点，写清：父节点、改动、**commit id**、结果、保留还是回退。

- **commit 建议真的提交**（`git commit -am "N5: ..."`）。只记 HEAD 但没提交的话，
  那个节点是**回不去**的——未提交的改动没法恢复。

## 尝试的结构（别原地打转）

迭代最容易在同一个想法上反复打转。用树来组织：

```
N1 基线
├─ N2 加注意力      ✓ 保留
│  ├─ N5 换骨干     ✗ 回退
│  └─ N6 调 loss    ✓ 保留   ← 当前
└─ N3 换数据增强    ✗ 回退
```

- 一个方向不行就**回到父节点**再试别的，别死磕
- 父节点也不行就**再往上退一层**（可能是更根本的假设错了）
- 同一模块可以并行试几种改法，各自一个分支

## 代码管理

- 不强制 commit，但**想回溯就必须提交**（见上面 tree.md）
- 决定回滚时 `git checkout <那个节点的 commit>`，并在 tree.md 里标 ✗ 回退
- 不要在一个失败上无限重试；试 2~3 次还不行就换方向，把原因写进死胡同

## 其他约定

- **起实验前必须先查显卡占用**，自己 ssh 查：
  `ssh {{SSH_ALIAS}} "gpustat"`（没装 gpustat 就用
  `nvidia-smi --query-gpu=index,memory.used,memory.total,utilization.gpu --format=csv`）
  只往**确认空闲**的卡上放实验——服务器上还有别人
- **并发上限见 `.auto/goal.md`**（多人共用的服务器务必设上限，不要占满）
- 不动别人的进程、文件、环境
- 登记超过 72 小时还没有 `DONE`，扩展会提醒——通常意味着崩了或忘了写 DONE

### SSH 使用纪律（排查问题必读）

- 排查服务器问题**可以自由用 ssh**（看日志、查进程、kill、nvidia-smi……），但必须走正门：
  `ssh {{SSH_ALIAS}} '<任意命令>'`（原生 ssh + `~/.ssh/config` 里配好的别名）
- 不要用**另一套环境里的 ssh**（比如 `wsl ssh`）——它有独立的钥匙和 known_hosts，会卡在指纹确认
- 也不要 `ssh 用户@裸IP`（绕过别名，同样卡交互确认）

## 调研

- 优先读本地 `refs/`（论文、repo 笔记）
- 需要查新东西时用联网搜索工具
- 外部模块/包在写进方案前先确认它真的存在

## 结果判读

- 多指标往往有权衡（例如主指标涨但副作用指标也涨），**由你判断值不值**，不要只看单一数字
- 具体看哪些指标、怎么算"变好"，按 `.auto/goal.md` 里我写的口径
